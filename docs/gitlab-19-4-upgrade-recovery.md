# GitLab 19.4 upgrade recovery boundaries

Applies to Eyrie `test` and `default` Helm releases and the independent Hawk Omnibus/Podman instance. This is an operational recovery plan, not permission to perform a destructive restore.

## Before each Eyrie chart step

Record the previous Helm revision and app version, confirm both CNPG clusters are Ready, both Ceph clusters are HEALTH_OK, and query the Rails batched background migration queue (must be zero before advancing). Verify the production scheduled `gitlab-backup` Job completed and its Bolt log says `Plan completed successfully with no result`; verify `/nest/backup/gitlab/latest_gitlab_backup.tar` resolves to a nonempty archive and `gitlab-secrets.yaml` exists on Falcon. Confirm the existing test restore and GitLab smoke checks, or repair a failed restore before advancing. Record object-storage availability and the actual Workhorse OCI digest for the target app version. The backup plan skips artifacts and registry payloads: do not describe the logical archive as a full-service disaster restore or the live object store as an independent copy. Check existing CNPG backup/WAL status, but do not impose a new off-RGW checkpoint, write outage, or isolated PITR drill as a prerequisite to this patch/minor upgrade. If the existing backup, object storage, database, or storage-health checks fail, investigate the concrete failure before migrating production.

A Helm revision rollback alone does not undo schema or data migrations. After a migration failure, freeze writes, preserve logs and release/DB state, assess whether forward repair to the intended version is possible, and only then choose a coordinated restore with the GitLab version matching the selected backup and its Rails secrets. The existing `nest::eyrie::gitlab::restore` plan is designed for the `test` refresh, not production: it deletes the Rails Secret and repositories. Do not invoke it against production. Its test refresh can restore an older production schema into a newer test image; the chart's previously completed migrations Job does not rerun on a same-version Helm deployment. Check for pending schema migrations and run them in test before checking webservice/Sidekiq readiness. Recheck CNPG readiness, Rails version, GitLab migrations, HTTPS/API, SSH Git, and registry. A restore loses writes made after that backup; do not silently revert production to an old binary against a migrated database.

The logical archive omits registry and artifact payloads and other object-storage features. Their independent full-service recovery is a separate reliability project, not a newly invented upgrade gate. Do not attempt to copy the approximately 1 TB registry into the shared RGW pool or confuse `/nest/backup/registry` (the separate standalone registry) with GitLab's registry. Do not promise recovery of skipped data from the application archive alone.

For physical recovery, create a *new* CNPG Cluster rather than rolling back the migrated cluster in place. Set `bootstrap.recovery.source` to an `externalClusters` entry using plugin `barman-cloud.cloudnative-pg.io`, `barmanObjectName: gitlab-cnpg-backups`, and `serverName: gitlab-cnpg` against the source namespace's ObjectStore. For PITR, set `bootstrap.recovery.recoveryTarget.targetTime` within the proven recoverability window; use the same PostgreSQL major version and an isolated PVC/cluster name. Keep the recovered cluster's WAL archiver unset until it has a separate destination, so it cannot overwrite the source WAL archive. Validate data and recovery timestamp before any traffic cutover. The plugin is a sidecar: enabling it on a running single-instance CNPG cluster replaces the Postgres pod and interrupts GitLab; stage the OBC and verify its rendered destination first. Rotating plugin mTLS certificates may require a plugin pod restart if its mounted certificate is not reloaded.

## Hawk separately

Check `sudo podman inspect gitlab` and Rails/DB versions, require zero batched migrations, run and verify a matching full GitLab backup and preserve `/srv/gitlab/config/gitlab-secrets.json` and `/srv/gitlab/gitlab.rb` with it outside the container's writable layer. Hawk's `/srv/gitlab` is a ZFS dataset; a pre-upgrade snapshot is an additional local recovery point, not a substitute for an independently stored archive. Verify `/nest/backup` NFS is mounted and copy the archive and secret/config to a restricted Hawk-specific directory there before applying the Puppet-managed image. Do not log secret contents. A post-migration binary/image rollback without restoring matching database and repositories is unsafe. On failure, freeze writes and use the version-matched backup with Omnibus `gitlab-backup restore` and its saved secrets/config (or an intact pre-upgrade ZFS snapshot if validated), then reapply source-managed Puppet and verify GitLab health. This is independent of Eyrie's CNPG and Ceph backup chain.

## Version progression

Eyrie production starts at chart 10.2.1 / GitLab 19.2.1. Test staged 10.2.7 / 19.2.7, 10.3.4 / 19.3.3, then 10.4.1 / 19.4.1; verify test health and restore before repeating the chart steps in production. Drain migrations at each step. Hawk has already moved from 19.3.2 to 19.4.1 with separate pre/post off-host backups; do not repeat its migration. GitLab 19.2 is the required stop before 19.4; future stops are 19.5, 19.8, and 19.11. Check upstream release notes and chart mappings again at execution. Single-replica Eyrie workloads are not a zero-downtime GitLab deployment.
